## 本次发现及修复

真实模型使用启用了自动审核的私有配置时，验收脚本仍只从 PENDING_APPROVAL 中选择候选并人工批准。实际最优候选已经自动批准，脚本却选择另一候选并产生审批冲突，错误地判定闭环失败。

本次只修正 `backend/scripts/validate_ai_tools.py`：优先接收已由规则批准的方案，未自动批准时保留原人工审批验证。验证审核来源，并在司机确认前检查隔离种子车辆的路线版本仍为 1。两条路径均需司机接收，之后分别回报到达和配送完成。不修改求解策略、业务审批规则、生产配置或团队数据库。

## 后端同学接下来做什么

1. 审核合并本次脚本小修复与报告。此前 PR #1 不要重复覆盖或再次合入。
2. 确认运行环境更新到了已合并的版本。默认 AGENT_MODE=local 和自动审核关闭，不等于模型接入代码缺失。
3. 在自己的私有根目录 .env 配置实际可用的模型端点、模型名及密钥：

```dotenv
AGENT_MODE=deepseek
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=填写自己账号实际可用模型名
DEEPSEEK_API_KEY=私下配置
AUTO_APPROVAL_ENABLED=true
AUTO_APPROVAL_MAX_CHANGED_ORDERS=2
AUTO_APPROVAL_MAX_DELAY_MINUTES=30
```

本次实际模型名为 deepseek-flash，只说明本机账户可用，不保证其他账户已开通。自动审核首版仅用于明确模拟数据，同车少量调序；真实数据仍人工审核。

4. 保留原 Compose 项目和数据卷，先备份，再重新构建及创建服务使配置生效。已有数据库不重复 seed，不执行 down -v：

```powershell
docker compose --env-file .env up -d --build --wait
```

确保 api、worker-compute、worker-chat、maintenance 使用一致配置；前端 API_PROXY_TARGET 指向实际后端地址，然后重新启动前端。

5. 在真实队列环境人工走一次聊天与方案流程，确认服务端模式、模型成功调用、司机接收前路线未变、接收后生效，再提供团队可访问的联调地址。
