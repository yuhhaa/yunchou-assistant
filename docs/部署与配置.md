# 部署与配置

## 本机地图配置

frontend/.env.local（可从.env.example复制，API_PROXY_TARGET默认指向本机8000）：

```dotenv
API_PROXY_TARGET=http://127.0.0.1:8000
VITE_AMAP_JS_KEY=填写自己申请的Web端JSAPI_Key
VITE_AMAP_SERVICE_HOST=/_AMapService
```

frontend/.env.amap-server.local（从.env.amap-server.example复制）：

```dotenv
AMAP_SECURITY_JSCODE=填写与该JS_Key配套的安全密钥
```

jscode只由Node开发服务器读取，不使用VITE_前缀。配置后完全重启npm run dev。当前前端Vite配置使用Node的loadEnvFile，因此沿用已验证的Node24环境。

底图配置成功后，/api/v1/map/demo提供武汉模拟点位与示意连线；不需要后端Web服务Key。它们不对应真实配送地址、道路或GPS，不用虚线距离计算ETA。候选图仅为预览，全部必要人工确认后才生效。

## 真实AI和道路

根目录私有.env按需填写：

```dotenv
AGENT_MODE=deepseek
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=填写账号实际开通的模型名
DEEPSEEK_API_KEY=填写自己的模型Key
AMAP_WEB_SERVICE_KEY=填写自己的高德Web服务Key
```

只启用需要的能力：未配置模型Key时保持AGENT_MODE=local。地图JS Key/jscode与地图Web服务Key不互换。

修改根目录.env后重新创建后端服务使环境变量生效。通过/map/geocode取得候选、人工确认后PUT /map/nodes/{node_id}维护真实GCJ02点位，再使用/map/route查询实际道路。显式/map/routing/refresh成功后计算才使用新真实矩阵；最多21点、总预算60秒、完整发布，失败不发布半张图。

本机 Vite 开发预览可在 `frontend/.env.amap-server.local` 追加 `AMAP_WEB_SERVICE_KEY`，启用模拟配送路线的道路贴合。此轨迹仅供展示。道路绕行方案继续从后端读取经过校验的路线，保持原始上报标记和避让范围。未配置此可选项时，模拟配送仍展示原示意连线。

### 现场拥堵绕行

1. 使用真实 API 登录模式，配置后端 `AMAP_WEB_SERVICE_KEY` 及前端高德 JS API 配置。用 `GET /api/v1/map?vehicle_id=V01` 查找配送节点及版本，通过 `PUT /api/v1/map/nodes/{node_id}` 确认同一片区的剩余站点坐标。演示数据可选武汉公开配送点。现场计算单独使用高德道路，不需要先刷新全车队矩阵。
2. 司机选择「上报异常 → 添加现场位置与拥堵路段」。获取一次 GPS 定位或在高德地图手动选点，再填写道路名称和行驶方向，点击拥堵起点、终点。GPS 在后端转换成 GCJ-02，位置有效期为 5 分钟。原有事件可以从事件详情补充或更新位置。
3. 调度员在异常详情点击「比较道路恢复方案」。等待方案保留配送顺序，并在高德预计用时之外计入上报的等待假设。绕行和调序方案核验道路轨迹是否与标记路段外接的缓冲区相交，再计算逐单到达时间和配送约束。行驶方向是现场说明，避让区对两个方向都生效。
4. 进入「查看轨迹与审批」，另一端用对应司机账号打开「待确认的调整」。调度批准后，由司机确认使方案生效。页面显示的是本轮计算时的位置与轨迹。路线版本随到站或订单完成更新后，需要重新计算剩余路段。

首版面向单车 1～5 个待配送站点，使用高德普通驾车规划。现场拥堵由司机或调度手动确认。`SIMULATION` 下的预计到达时间沿用演示业务时钟。

### 离线评测道路恢复

进入 `backend` 后运行 `uv run python -m scripts.road_benchmark --output ../road-benchmark-results`。评测覆盖 28 个固定模拟案例，包含轻度延误、严重延误、绕行无收益、无绕行、需要改序、硬时间窗和无可行道路。输出 CSV 明细和 JSON 汇总。

可选参数 `--recorded-case <本地路段耗时记录.json>` 会加跑武汉实测道路成本的回放。回放仍使用模拟配送订单和人为标记的拥堵范围，汇总与纯模拟案例分开。评测固定道路用时、配送订单和业务时钟。仅等待策略加计一次额外等待，未求得的方案保留空指标。计时覆盖整案求解，单独排除地图请求、队列等待、审批和司机确认时间。

### 道路绕行接口衔接

- 浏览器使用登录 JWT。提交与更新走 `POST /api/v1/incidents`，`road_report` 包含 `location` 和 `congestion`。地图选点用 `GCJ02`，浏览器 GPS 用 `WGS84`，由后端转换。`captured_at` 填报点的当前时间。
- 调度员调用 `POST /api/v1/incidents/{incident_id}/road-recovery`，传当前的 `expected_incident_version`。用返回的 `job_id` 查询 `/api/v1/jobs/{job_id}`，成功后读取事件 `/workspace`。道路比较位于 `analyses[].road_comparison`，可审批候选位于 `plans`；对应方案由 `snapshot_id` 和 `metrics.road_strategy` 区分。
- 使用 `/api/v1/map/route` 读候选或已生效的轨迹。地图要支持 `LineString`、`MultiLineString` 和空值。多段轨迹分开绘制；`reported_origin` 用于放置上报位置标记。
- 写操作使用 `Idempotency-Key`。审批与司机回执以服务端返回的事件、快照和方案版本为准。只有司机接受后才将方案显示为生效。

### Windows Docker API 端口

如果 Docker 绑定本机 `8000` 失败，运行 `netsh interface ipv4 show excludedportrange protocol=tcp` 检查 Windows 保留区间。任选一个可用端口，例如在项目私有 `.env` 设置 `API_PORT=18080`。然后重新创建 API 服务以应用端口映射。前端在自己的 `.env.local` 将 `API_PROXY_TARGET` 改为 `http://127.0.0.1:18080`，再重新启动前端。后端容器内部端口仍是 `8000`。端口修改可沿用现有数据库卷。

## 已有环境与数据

可选的恢复方案规则审核见[自动审核接入说明](自动审核接入说明.md)。AUTO_APPROVAL_ENABLED 默认 false；启用后仅对符合规则的模拟候选自动预留，仍需司机确认才生效。API、计算及聊天 worker、维护器须使用一致开关及阈值。真实业务或真实路网候选继续人工审核。

升级前备份并停止旧API、worker、维护器，再docker compose --env-file .env up -d --build --wait，迁移容器自动增量升级至0004。不要删除数据卷或重新seed以代替升级。

普通停止docker compose --env-file .env down，保留卷。恢复时沿用相同.env与Compose项目名。固定基准验证脚本backend/scripts/demo.py会修改业务数据，仅在全新隔离演示库运行一次。

## 生产部署

后端支持外部PostgreSQL/Redis，华为云RDS/DCS连接模板见deploy/huaweicloud。模板不代表已开通云资源。

前端npm run build生成dist。生产静态站点需反向代理/api到后端，并实现同源/_AMapService及/_AMapService/_status，安全密钥由服务端注入。当前仓库的server/amapProxy.ts是Vite开发中间件，vite preview和纯静态托管不会运行它。不要把AMAP_PROXY_TARGET指向尚未实现此代理的业务API。

仅在配置和上游已核验后才应由生产代理返回configured:true。正式环境需要固定允许上游、请求路径和方法限制、超时、体积上限、限流、错误脱敏、不转发业务JWT/Cookie及禁止在日志记录jscode。HTTPS证书、域名、备份与资源权限按实际环境配置。

本仓库提供可复现的本机演示与后端云连接模板；未承诺未经验证的生产代理、真实模型效果、道路货车限制或比赛合规结果。
