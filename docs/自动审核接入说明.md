# 恢复方案规则自动审核

方案由后端计算，大模型负责理解异常和解释结果。启用本功能后，后端对新生成候选执行确定性规则审核；司机仍需确认，之后才更新有效路线。现有候选不会被批量追溯批准。

## 默认规则 AUTO_RESEQUENCE_V1

- 仅道路延误 ROAD_DELAY，报告延误不超过 30 分钟。
- 仅事件车辆内部调序，调整订单数为 1 至 2，不能跨车辆转单。
- 约束检查通过，没有未解决订单、迟到订单、高优先级延误或转单。
- 相对原方案不增加距离。
- 复用现有审批中的快照、版本、目标路线和车辆资源预留检查。

多候选符合规则时，按总延误、调整订单数、额外距离、方案编号顺序选取一个。阈值是本项目首版策略，不是运输安全标准；上线前由团队按实际业务确认。模拟路网计算结果不能当作真实道路导航。

## 配置与部署

后端及 Celery worker 使用一致配置，修改后一起重启：

```dotenv
AUTO_APPROVAL_ENABLED=true
AUTO_APPROVAL_MAX_CHANGED_ORDERS=2
AUTO_APPROVAL_MAX_DELAY_MINUTES=30
```

源码模板和两套 Compose 已加入配置。默认 false，保持原有人工审批。关闭开关只影响后续候选，不撤销已经批准或已经生效的方案。不需要数据库结构迁移，也不需要给大模型添加审批工具。

## 状态和前端对接

1. 生成符合条件的候选 → APPROVED_PENDING_ACK，事件 AWAITING_ACK。
2. 司机端通过既有工作空间刷新获取待确认方案，点击接收并通过后端复核 → ACTIVE。
3. 不符合规则或审批校验冲突 → PENDING_APPROVAL，仍由调度员审批。无可行方案沿用 MANUAL_REVIEW。
4. 司机拒绝、超时、过期与版本冲突沿用既有生命周期处理。预留窗口较短，司机需及时确认；超时后刷新上下文重新计算。

PlanOutput 新增 approval_mode：AUTOMATIC_RULE 表示规则审核，MANUAL 表示人工审批，null 表示尚未审批。司机页面和流程账本已显示审核来源。旧接口调用方式不变。

自动审核使用不可登录的内部策略身份 SYSTEM_AUTO_RESEQUENCE_V1，AuditEvent 记录 auto_approval_decision、策略版本、阈值、逐候选拒绝原因、选中方案或审批冲突原因；同时保留既有 approve_plan 审计。

## 验收步骤

使用干净的模拟数据和真实登录账号，上报 O001 道路延误 20 分钟，完成影响分析、生成恢复候选；符合条件时应直接显示等待司机确认。在司机确认前核对路线版本未增加，接收后才生效。将最大调整数改成 1，重新生成候选，验证转回人工审批。运行 tests/test_auto_approval.py 验证默认关闭、阈值、拒绝跨车、审批冲突、司机确认和重复任务不重复批准。

SQLite 自动化测试用于功能回归；PostgreSQL 多 worker 并发、崩溃恢复和云端真实账号联调仍需部署环境验收。
