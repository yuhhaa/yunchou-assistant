# 运筹助手：两项流程调整与交接说明

日期：2026-11-08。本文区分本机已经实现的功能与建议开发项，不代表团队服务器已经更新。

## 1. 简单恢复方案自动审核，司机确认后执行

目标：减少每一次恢复方案都等待调度员的环节。由后端验证方案是否符合规则，符合条件直接发给司机确认；复杂方案和冲突仍保留人工审批。大模型负责理解异常和解释结果，不拥有自主审批权。

新流程：异常上报 → 信息补齐 → 影响分析 → 恢复候选 → 后端规则审核 → 司机接收 → 后端复核并生效 → 执行反馈。

当前本机已实现、已开启，并通过自动化验证。范围限定为 ROAD_DELAY、延误不超过 30 分钟、同车调序 1～2 单、无迟到及未解决订单、不增加距离、约束检查通过。不满足条件保留 PENDING_APPROVAL；没有可行方案沿用 MANUAL_REVIEW。这不是所有“看起来没问题”的方案都自动通过。

### 后端同学需要做什么

需要合入代码和配置；仅在你电脑上实现，不会自动同步到后端同学或团队部署。

1. 接收 `自动审核交付_20261108.zip`，先阅读其中 `docs/自动审核接入说明.md`。
2. 若尚未合入此前真实模型、聊天状态和候选生成修复，同时接收 `AI真实接入验收交付_20261107.zip`；按团队当前分支逐文件比对合入，避免整个目录覆盖掉后续修改。
3. 核对核心文件：`backend/app/services/auto_approval.py`、`jobs.py`、`common.py`、`backend/app/config.py`、`outputs.py`，以及 OpenAPI、前端类型和审核来源提示。
4. 后端 API 与 Celery worker 一起配置、一起重启：

```dotenv
AUTO_APPROVAL_ENABLED=true
AUTO_APPROVAL_MAX_CHANGED_ORDERS=2
AUTO_APPROVAL_MAX_DELAY_MINUTES=30
```

5. 默认模板为 false。上线前由团队确认规则阈值，再开启；当前功能无新增数据库结构迁移。
6. 在 PostgreSQL/Redis/Celery 环境补测重复投递、并发候选、资源冲突、重启恢复、预留超时、多租户权限。

复用原审批的快照、版本、路线约束和资源预留校验。结果为 APPROVED_PENDING_ACK / WAITING_ACK，不能直接视为 ACTIVE。司机接收后才允许更新有效路线。司机拒绝或预留过期沿用原生命周期逻辑，不应由前端绕过。

新增 `approval_mode`：AUTOMATIC_RULE / MANUAL / null；前端区分“规则自动审核”和“调度员审批”。AuditEvent 保留审核策略、阈值、候选拒绝原因和最终选择。

## 2. 补齐车辆位置与拥堵路段，区分调序和绕行

问题确认：当前司机账号绑定车辆，后端持有车辆 `location_node_id` / `location_time`，到站反馈会更新位置。它是最近确认业务节点，不是实时 GPS。高德底图已接入，但模拟节点、配送连线和路网计算没有因此变成真实道路规划。ROAD_DELAY 目前主要把预计延误加到出发时间，再比较配送顺序。

因此当前支持的是“已知延误后的模拟配送调序”，不能宣称“识别具体拥堵路段并绕行”。只提供延误分钟数可以用于调序估算，但不足以进行真实道路绕行。

### 建议流程（尚未实现）

司机上报 → 获取授权位置并校验新鲜度 → 确认异常道路或地图点位 → 补齐延误等信息 → 按真实路网计算影响及候选 → 显示位置来源、路线、ETA 和调整原因 → 审核 → 司机确认执行。

位置不明确时，应补问“您在哪条道路、哪个路口附近？也可以授权定位或在地图标记”。不能从订单目的地推断车辆当前位置，也不能把“最近站点”当作实时定位。

### 后端负责

- 定义车辆位置上报接口及鉴权：只允许授权司机上报所属车辆；保存经纬度、坐标系、采集时间、精度、来源、服务端接收时间。
- 定义拥堵证据：道路名称、方向/路段或标注坐标、报告时间、预计延误、司机报告来源。字段和接口名称由团队统一，本文不将建议字段当作现有接口。
- 校验位置过期、低精度、未来时间和不合理跳变。过期阈值需结合定位方式约定；失败时返回补问或人工选点，不静默退回仓库坐标。
- 接入道路规划或通行时间服务，提供真实路网距离/时间供影响分析和求解使用，而不仅绘制一条高德道路线。单纯换底图或画线不能完成算法接入。
- 区分车辆实时位置、最近确认站点、异常点位和目的地，统一高德所需坐标系，防止重复转换。
- 规划请求在安全的服务端执行、缓存和限流；新增输入应进入快照及版本校验，位置或路况显著变化时使旧候选失效。
- 不能承诺任意地图点选都支持精确避开整段道路；需核对选用服务的避让能力，并验证候选确实绕开相关路段。
- 真实数据模式下，若位置/路况不足，禁止按模拟证据自动审核；应返回补问、人工处理或明确标注的降级结果。此门禁需要新增，当前首版规则主要运行在模拟配送数据上。

### 前端负责

- 安全停车后授权定位；显示位置时间和精度，允许刷新、拒绝定位或手动选点。定位通常需要 HTTPS 或 localhost。
- 在异常入口增加道路/路口说明、定位或地图标记；提示当前采集不足的项目。
- 地图分别展示当前车辆位置、异常位置、剩余订单和候选道路路线。
- 区分“调整配送顺序”和“道路绕行”，展示距离/ETA 的数据来源；不要把示意连线当导航。

### AI 接入负责

- 提取道路、方向、附近地标、延误等信息；无法定位时补问。
- 只调用后端定位/地理解析结果作为可信坐标，不能自己编造坐标或道路通行状态。
- 按后端返回的数据来源解释建议，不对模拟结果作真实绕行承诺。

建议分两阶段：先补“位置采集、异常点位和来源提示”；再补“真实道路通行时间、求解输入和候选路线”。两项都需要后端参与，不能仅靠前端或提示词完成。

## 团队验收标准

自动审核：合格候选无需调度员操作；司机确认前路线版本不变，确认后生效；超阈值、跨车和冲突不自动通过；审计可追踪。

位置与路段：无有效位置时明确补问；定位拒绝可选点；坐标系及时间一致；真实候选使用位置和道路数据参与计算；地图显示与返回路线一致；模拟模式始终可识别。
